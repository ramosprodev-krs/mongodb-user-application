### 🔐 JWT Architecture & Security Flow

This document details the internal structure and technical implementation of JSON Web Tokens (JWT) within the **Auth User API** security layer.

1\. 🏗️ The Token Structure (RFC 7519)
--------------------------------------

Every token generated by this API follows the standard segments encoded in Base64URL:

-   **Header**: Specifies the hashing algorithm (HS256).

-   **Payload (Claims)**: The core data of the token. In this project, it contains:

    -   `sub`: The subject (the **username** from `UserEntity`).

    -   `role`: A list of the user's specific authorities retrieved from the `userRoles` set.

    -   `iat`: Issued-at timestamp.

    -   `exp`: Expiration timestamp (defined by `jwt.expiration`).

-   **Signature**: Created by hashing the header and payload with a secret key using **HMAC-SHA256**. This ensures data integrity---any change in the payload invalidates the signature.

2\. 🛡️ Spring Security & MongoDB Integration
---------------------------------------------

The application uses a **Stateless Authentication** model. Each request is independent and verified against the MongoDB-backed user store.

### 2.1. The Authentication Filter

Before reaching any Controller, the request passes through the `SecurityFilter`:

1.  **Extraction**: Identifies the `Authorization` header.

2.  **Format**: Validates the `Bearer <token>` format.

3.  **Verification**: The `TokenService` validates the signature using `Keys.hmacShaKeyFor(secretKey.getBytes())`.

4.  **Context**: If valid, the user's identity is injected into the `SecurityContextHolder` to allow access to protected routes.

3\. Role-Based Access Control (RBAC)
------------------------------------

The JWT acts as a digital passport, carrying specific clearance levels mapped from the `UserRole` enum in MongoDB.

| Role | Access Level | Description |
| --- | --- | --- |
| **ROLE_USER** | Basic | Standard access to user-specific endpoints. |
| **ROLE_ADMIN** | Full | Total system access, including management and sensitive configurations. |

⏳ 4. Security Constraints & Implementation
------------------------------------------

### 4.1. Statelessness

The server does not persist tokens in the MongoDB database. It relies on **Cryptographic Trust**.

-   **Implementation**: `SecurityConfiguration` defines the policy as `SessionCreationPolicy.STATELESS`.

-   **Impact**: Every request must carry its own "proof of identity", which the server verifies on the fly.

### 4.2. Expiration (TTL)

Tokens are designed with a short-lived strategy to mitigate the risk of token theft.

-   **In the code**: The `TokenService` calculates the `exp` claim using `System.currentTimeMillis() + expirationTime`.

-   **Impact**: Once the expiration is reached, the JWT parser will reject the request, requiring a new login.

### 4.3. Validation Logic

The `validateToken` method uses the `SigningKey` to decode and verify the payload:

Java

```
public String validateToken(String token) {
    return Jwts.parser()
            .verifyWith((SecretKey) getSigningKey())
            .build()
            .parseSignedClaims(token)
            .getPayload()
            .getSubject();
}

```

🛠️ Core Security Components
----------------------------

1.  **`UserEntity`**: Implements `UserDetails`, mapping MongoDB documents to Spring Security users. Includes validation for **CPF**, **Email**, and **Username**.

2.  **`TokenService`**: Handles the generation and verification of JWTs using the `jjwt` library.

3.  **`SecurityConfiguration`**: Orchestrates the filter chain, sets BCrypt as the password encoder, and manages endpoint permissions.
